# vanity-gpu

[English](README.md) | **Русский**

Генератор красивых адресов на CUDA для EVM (Ethereum, BSC, Polygon, Arbitrum и других: адрес один на все сети), TRON, Bitcoin (`bc1q…`, `1…`, `3…`), Solana и TON (кошелёк W5).

Скорость на RTX 3090:

| сеть | скорость | 4 символа | 6 символов | 8 символов |
|------|----------|-----------|------------|------------|
| EVM (hex)       | ~1.9 Гключ/с | мгновенно | ~10 мс  | ~2 с   |
| TRON (base58)   | ~1.8 Гключ/с | мгновенно | ~20 с   | ~19 ч  |
| Bitcoin `bc1q…` (bech32) | ~3.9 Гключ/с | мгновенно | ~0.3 с | ~5 мин |
| Bitcoin `1…` (base58)    | ~3.8 Гключ/с | мгновенно | ~10 с  | ~9.5 ч |
| Bitcoin `3…` (base58)    | ~2.1 Гключ/с | мгновенно | ~18 с  | ~17 ч  |
| Solana (base58) | ~255 Мключ/с | мгновенно | ~2.7 мин | ~6 дней |
| TON (base64)    | ~210 Мключ/с | мгновенно | ~5.5 мин | ~16 дней |

Время в таблице — это среднее ожидание для префикса без учёта регистра в EVM. Перед стартом программа сама показывает ожидаемое время для вашего шаблона. Суффиксы TRON медленнее (~1.1 Гключ/с): для них нужна контрольная сумма адреса (двойной SHA-256). EVM и TRON упираются в keccak-256, который на 3090 работает на ~80% пиковой целочисленной производительности. Перенос его поворотов на умножители (IMAD, отдельный конвейер) проверен: так на 1–12% медленнее, `mul.hi` на этой карте работает вдвое медленнее. Bitcoin вдвое быстрее: SHA-256 + RIPEMD-160 от сжатого ключа дешевле keccak. Адрес `3…` считает hash160 дважды, поэтому медленнее. Окончания `bc1q…` (~3.0 Гключ/с) требуют контрольной суммы bech32.

Solana и TON при старте строят таблицу умножения на 2.4 ГБ видеопамяти (~3 с, на это время ~2.5 ГБ ОЗУ). Если свободной видеопамяти меньше ~5.5 ГБ, берётся малая таблица на 50 МБ: скорость примерно на 25% ниже.

## Сравнение с другими генераторами

Замерено на одной и той же RTX 3090 (драйвер 595, CUDA 12.4) подряд, на прогретой карте, шаблоном, который заведомо не найдётся. Чужие программы собраны из исходников с GitHub (ноябрь 2026) и запущены в их режиме бенчмарка или поиска.

| сеть | программа | скорость | ключи |
|---|---|---|---|
| EVM | **vanity-gpu** | **1.80 Гключ/с** (1.92 с `--cpu max`) | getrandom, split-key, проверка каждой находки на CPU |
| EVM | [vanity-eth-address](https://github.com/MrSpike63/vanity-eth-address) | 1.63 Гключ/с | `/dev/urandom`, полный ключ на GPU |
| EVM | [ProVanity](https://github.com/WooMai/ProVanity) 1.1.2 | 1.11 Гключ/с | в README не описано |
| EVM | [profanity2](https://github.com/1inch/profanity2) | 0.84 Гключ/с | split-key |
| TRON, начало | **vanity-gpu** | **1.78 Гключ/с** | как выше |
| TRON, начало | ProVanity | 0.99 Гключ/с | |
| TRON, окончание | **vanity-gpu** | **1.07 Гключ/с** | |
| TRON, окончание | ProVanity | 0.75 Гключ/с (не длиннее 8 символов) | |
| Bitcoin `1…` | **vanity-gpu** | **3.79 Гключ/с** | |
| Bitcoin `1…` | [VanitySearch](https://github.com/JeanLucPons/VanitySearch) | 3.87 Гключ/с | случайный базовый ключ, split-key по желанию |
| Bitcoin `bc1q…` | **vanity-gpu** | **3.85 Гключ/с** | |
| Bitcoin `bc1q…` | VanitySearch | 3.87 Гключ/с | |
| Bitcoin `3…` | **vanity-gpu** | **2.19 Гключ/с** | |
| Bitcoin `3…` | VanitySearch | 2.00 Гключ/с | |

ProVanity собран с CUDA 13.5 и замерен своей командой `provanity bench` (60 с, автоподбор параметров). TRON — его интерактивным поиском с недостижимым шаблоном.

- **EVM**: на 10% быстрее самого быстрого из найденных генераторов, в 1.6 раза быстрее ProVanity и вдвое быстрее profanity2. Узкое место у всех — keccak.
- **Bitcoin**: на равных с VanitySearch (−2%…+9%). Это тот же класс алгоритма: обход соседних точек, пакетная инверсия, эндоморфизм. VanitySearch ищет только начало адреса, здесь есть ещё окончания, `--beauty` и списки.
- **Solana**: solanity (ChorusOne) в README сам предупреждает, что не использует криптостойкий генератор случайных чисел, и ключи из него небезопасны. Форк mcf-rocks берёт энтропию у ОС и пишет, что 5 символов на Tesla V100 находятся в среднем за 12 минут. Здесь на RTX 3090 это ~3 секунды. Карты разные, но разница на порядки.
- **TON**: генераторов ключей кошелька на GPU не нашлось: vaniton перебирает мнемоники на CPU. [ton-org/vanity](https://github.com/ton-org/vanity) намного быстрее, но решает другую задачу: подбирает соль для адреса смарт-контракта, который потом нужно задеплоить. Обычный кошелёк, импортированный по ключу, будет на другом адресе.
- **TRON**: из найденных TRON умеет только ProVanity. Мы быстрее в 1.8 раза для начала адреса и в 1.4 раза для окончания, и окончание у нас любой длины.
- Ни один из них не ищет несколько сетей за один проход и не сравнивает «красоту» разных сетей по редкости.

## Сборка

```bash
cmake -S . -B build && cmake --build build -j
./build/vanity-gpu selftest
```

Нужны CUDA 12.x и g++-13: nvcc 12.4 не поддерживает gcc 15, CMake сам возьмёт g++-13. Видеокарта по умолчанию — sm_86 (RTX 30xx). Для другой задайте `-DCMAKE_CUDA_ARCHITECTURES=89` (40xx) или `120` (50xx).

Требования, параметры, готовые сборки и сборка на GitHub Actions: [docs/BUILD.ru.md](docs/BUILD.ru.md). Все замеры и как запускались конкуренты: [docs/BENCHMARKS.md](docs/BENCHMARKS.md).

## Использование

```bash
vanity-gpu evm dead..beef            # начинается с dead, заканчивается на beef
vanity-gpu evm 0x00000000 -n 5       # 5 адресов
vanity-gpu evm '??c0ffee'            # ? — любой символ
vanity-gpu tron TRX..888             # TRON: base58, регистр важен
vanity-gpu sol Pump ..pump           # несколько шаблонов за один запуск
vanity-gpu ton cool                  # TON: UQ?cool...
vanity-gpu ton UQAAAA                # TON: UQ + AAAA
vanity-gpu evm --beauty --min-score 14 -n 0   # «красивые»: длинные повторы в начале и в конце
vanity-gpu sol -f words.txt -n 0     # список шаблонов из файла (хоть 100 000 строк)
vanity-gpu sol elon -i -l            # примерно: ELoN, E1on, 3lon, 31oN ...
vanity-gpu evm coffee -l             # o → 0: c0ffee, c0ff33 ...
vanity-gpu ton '[Tt][Oo]n..[Tt]on'   # [..] — любой из перечисленных символов
vanity-gpu evm dead --cpu max        # + все ядра процессора (≈ +7%)
vanity-gpu btc bc1qdead              # Bitcoin native SegWit (bech32: нет 1 b i o)
vanity-gpu btc 1Love                 # Bitcoin legacy; тип адреса берётся из шаблона
vanity-gpu btc 3Cat ..cat            # Bitcoin P2SH-SegWit
vanity-gpu evm --only digits         # адрес из одних цифр (весь — за доли секунды)
vanity-gpu evm --only upper --min-score 16     # длинные серии ЗАГЛАВНЫХ в EIP-55-виде (~20 с)
vanity-gpu sol --only lower+digits   # без заглавных букв
tools/wordlist.sh -m 8 > words.txt   # словарь из установленного aspell
vanity-gpu sol -f words.txt -c -l --at both -n 0   # слова + мутации в начале и в конце
```

## Списки, словари и мутации

- **`-f ФАЙЛ`** — шаблоны из файла, по одному на строку; `#` начинает комментарий. Синтаксис тот же, что в командной строке: `слово`, `..слово`, `нач..кон`, `?`, `[..]`. Неверные строки пропускаются с объяснением, остальные ищутся.
- **`--at start|end|both`** — куда ставить простые слова из списка: в начало (по умолчанию), в конец или и туда и туда.
- **`--min-len N`** — пропустить слова короче N символов. Короткие слова находятся тысячами в секунду и только засоряют результаты.
- **`[abc]`** — в этой позиции подходит любой из символов: `[aA4]pple`.
- **`-c`** — три формы слова: `word`, `Word`, `WORD`. Обычно этого достаточно, и вариантов намного меньше, чем с `-i`.
- **`-i`** — буквы в любом регистре в каждой позиции (TRON, Solana, TON, Bitcoin `1…`/`3…`; в EVM и `bc1q` регистра нет).
- **`-l`** — похожие символы: `o=0`, `i=l=1`, `z=2`, `e=3`, `a=4`, `s=5`, `b=6=G`, `t=7`, `B=8`, `g=9`. Варианты, которых нет в алфавите сети, отбрасываются. Поэтому EVM-шаблон `coffee -l` ищет `c0ffee`, `c0ff33` и так далее, а без `-l` программа подскажет, что `o` в hex не бывает.
- **`--subs N`** — не больше N изменённых символов на слово (регистр или похожий символ). Для строк из файла по умолчанию 3, для шаблонов в командной строке без ограничения. Без этого 12-буквенное слово с `-l` даёт сотни тысяч нечитаемых вариантов вроде `3x4mp135`.

Каждый вариант — отдельный шаблон: `elon -i -l` на Solana даёт 18 вариантов, и все ищутся одновременно. При старте программа пишет, сколько шаблонов получилось и сколько ключей в среднем уходит на одну находку. Если находок ожидается больше ~20 в секунду, она предупреждает об этом.

### Откуда брать словари

- `tools/wordlist.sh` собирает список из словарей aspell, которые уже установлены (английский — около 127 тысяч слов с формами): `tools/wordlist.sh -m 8 > words.txt`. Ключи: `-d ru` и т. п. — другой словарь (`aspell dicts`), `-f файл` — добавить свой список, `-m`/`-M` — длина, `-t evm|btc|base58|ton` — только слова, которые подходят сети без `-l`.
- `examples/words-crypto.txt` — около ста крипто-слов (moon, hodl, wagmi, satoshi, …).
- Любой текстовый файл со словами по одному на строку. Например, большой английский список `words_alpha.txt` (github.com/dwyl/english-words, ~370 тысяч слов) или список BIP-39. Скачайте его сами и передайте через `-f`.

### Как это устроено и сколько стоит

До 16 шаблонов проверяются по одному. Длинные списки идут через индекс в видеопамяти. Из адреса берутся первые и последние символы, битовая карта (до 512 МБ) одним обращением отсекает почти все адреса, остальные проверяются двоичным поиском. Варианты слов генерируются один раз при старте, а на каждый ключ проверка стоит O(1) независимо от размера списка. Генерировать варианты прямо на GPU поэтому не нужно: узкое место — математика ключей, а не перебор слов.

Чистое слово в начале или в конце («key-only») хранится в индексе без дескриптора: GPU проверяет только 64-битный ключ, а символы за его пределами досматривает CPU (ложные кандидаты выпадают ~раз в несколько минут и отбрасываются молча). Поэтому шаблон занимает в памяти около 400 байт, пока список компилируется, и около 60 байт видеопамяти. Предел — 20 млн вариантов (`--max-patterns`). Перед генерацией программа быстро считает, сколько вариантов получится, и сразу сообщает, если их слишком много.

| словарь aspell, -c -l | вариантов | скорость | ОЗУ на старте |
|---|---|---|---|
| Solana, слова ≥ 9 букв | 11.7 млн | 238 Мключ/с (без потерь) | 5.6 ГБ, ~15 с |
| TRON, ≥ 10 букв, начало и конец | 13.7 млн | 725 Мключ/с (окончания требуют контрольной суммы) | 4.7 ГБ, ~30 с |
| Bitcoin `bc1q`, ≥ 10 букв, начало и конец | 0.7 млн | 2.7 Гключ/с | 0.75 ГБ |

Шаблон должен иметь хотя бы один фиксированный символ в начале (после `T` / `UQ?` / `bc1q` / `1` / `3`) или в конце. Шаблонов вида `?abc` без фиксированного начала и конца в одном запуске может быть не больше 16.

## Только цифры, только буквы (`--only`)

`--only КЛАСС` ищет адреса из символов одного вида: `digits`, `lower`, `upper`, `letters`, их сочетания через `+` (`digits+upper`) или сами символы (`0-9A-F`). Оценка — длина ведущей серии таких символов плюс длина замыкающей. Если подходит весь адрес, оценка равна его длине. Порог задаёт `--min-score`. По умолчанию порог выбирается так, чтобы находка была примерно раз в 30 секунд, или весь адрес, если это ещё проще. Для удобства при старте показано, какие символы попали в класс и сколько позиций считается.

- **EVM**: регистр — это регистр контрольной суммы EIP-55, в котором адрес показывают MetaMask и Etherscan. `upper` — заглавные `A-F`, `lower` — строчные. Адрес из одних цифр (`--only digits`, 40 из 40) находится за доли секунды, а адрес без строчных букв (`--only digits+upper`) — мгновенно.
- **TRON, Solana, Bitcoin `1…`/`3…`, TON**: регистр как в адресе. Второй символ TRON почти всегда заглавный, это учтено в оценке времени.
- **Bitcoin `bc1q`**: регистра нет, `upper` и `lower` значат одно и то же — буквы.

`--beauty` (серии одного символа) и `--only` — два разных режима оценки; в одном запуске работает какой-то один.

## Несколько сетей за один проход (`multi`)

EVM, TRON и все три типа Bitcoin получают адрес из одного и того же ключа secp256k1. Самая дорогая часть — обход точек кривой. Она делается один раз, а для каждой сети считается только её хэш: keccak у EVM и TRON общий, hash160 общий у всех типов Bitcoin. У Solana и TON общий ключ ed25519. Смешать secp256k1 и ed25519 в одном проходе нельзя: это разные ключи.

```bash
vanity-gpu multi evm,tron,btc --beauty -n 0 --cpu max      # красивые адреса в трёх сетях сразу
vanity-gpu multi evm,tron,btc --beauty --rarity 40 -n 0    # реже и красивее: ~1 из 2^40 в каждой сети
vanity-gpu multi btc-all --beauty -n 0                     # bc1q, 1… и 3… одновременно
vanity-gpu multi sol,ton --only digits -n 0
vanity-gpu multi evm,tron,btc ..777 evm:dead btc:bc1qcafe  # шаблоны: общий и для одной сети
```

- Сети: через запятую. Сокращения: `secp` = `evm,tron,btc`, `btc-all` = `btc,btc-legacy,btc-p2sh`, `ed` = `sol,ton`.
- Шаблон `сеть:ШАБЛОН` ищется только в этой сети. Шаблон без префикса ищется во всех сетях, где он допустим. Например, `..777` подходит для любой сети, а `dead` только для EVM. Строки списка `-f`, недопустимые для какой-то сети, в ней пропускаются.
- Найденный адрес печатается с названием сети. Ключ от него — обычный ключ этой сети, импорт такой же, как при поиске в одной сети.

**Одинаковая «красота» для разных сетей.** Оценка 10 значит в разных сетях очень разное. Серия из 10 одинаковых hex-символов EVM встречается намного чаще, чем серия из 10 символов base58 TRON: у EVM 16 вариантов символа, у Bitcoin `bc1q` 32, у TRON и Solana 58, у TON 64. Поэтому в `multi` порог задаётся редкостью в битах: `--rarity 40` значит, что адрес такой красоты встречается примерно 1 раз на 2^40 ≈ 1.1·10^12 ключей. Для каждой сети выбирается оценка, ближайшая к этой редкости:

| `--rarity` | EVM | Bitcoin `bc1q` | TRON, `1…`, `3…`, Solana | TON |
|---|---|---|---|---|
| 36 (по умолчанию; для sol,ton — 32: оценки 8 и 8) | 12 (2^36.6) | 10 (2^36.9) | 9 (2^38.0) | 8 (2^33.2) |
| 40 | 13 (2^40.5) | 11 (2^41.7) | 9 (2^38.0) | 9 (2^39.0) |
| 44 | 14 (2^44.4) | 11 (2^41.7) | 10 (2^43.7) | 10 (2^44.9) |

Оценка меняется только целыми шагами: у EVM шаг 4 бита, у Bitcoin 5, у base58 5.9, у TON 6. Поэтому совпадение приблизительное, до ±3 бит. Точная редкость каждой находки печатается рядом с ней, например `beauty score 13 (1 in 2^40.5)`. По ней находки из разных сетей можно сравнивать между собой. Задать оценку для отдельных сетей вручную: `--min-score evm=14,tron=10`. Остальные сети тогда берут порог из `--rarity`. `--rarity` работает и при поиске в одной сети, вместо `--min-score`. Для `--only` редкость работает так же.

**Скорость** (RTX 3090), на каждую сеть. «По очереди» — те же сети отдельными запусками, по равному времени на каждую.

| сети | шаблоны | `--beauty` | по очереди, `--beauty` |
|---|---|---|---|
| evm,tron | 1.6 Гключ/с | 1.0 Гключ/с | 0.7 Гключ/с |
| evm,tron,btc | 1.15 Гключ/с | 0.8 Гключ/с | 0.56 Гключ/с |
| evm,tron,btc-all | — | 0.46 Гключ/с | 0.3 Гключ/с |
| sol,ton | — | 210 Мключ/с | 114 Мключ/с |

Красота в TRON и `1…`/`3…` дороже, чем шаблон в начале. Последние символы адреса зависят от контрольной суммы (двойной SHA-256), поэтому её нужно считать для каждого ключа.

## Процессор и встроенная видеокарта

`--cpu N` (или `--cpu max` — все потоки, кроме одного) запускает поиск EVM/TRON/Bitcoin ещё и на процессоре. Процессор идёт по своим участкам той же split-key схемы. Keccak считается для 8 ключей сразу на AVX-512, SHA-256 + RIPEMD-160 — для 16. Каждая находка процессора перепроверяется так же, как находки GPU.

На Ryzen 7 7800X3D: 13 Мключ/с на поток, 136 Мключ/с на 15 потоках. Вместе с 3090 это EVM 1.89 → 2.02 Гключ/с и TRON 1.82 → 1.94 Гключ/с, то есть +7%. Для Bitcoin `bc1q`: 3.86 → 4.0 Гключ/с (+4%). Процессор при этом греется на полную мощность. Для окончаний TRON прирост около 3%: процессору приходится строить base58-строку на каждый ключ.

Для Solana и TON `--cpu` не используется: ed25519 на процессоре дал бы меньше 1% к видеокарте.

Встроенная видеокарта Radeon (Raphael, 2 вычислительных блока) не поддерживается намеренно. Её целочисленная мощность примерно в 30 раз меньше, чем у 3090, это +2–3% в лучшем случае. Для неё пришлось бы переписать все ядра под Vulkan. Кроме того, она делит с процессором один лимит мощности, поэтому вместе с `--cpu` прибавка была бы ещё меньше.

## Результаты

Найденное дописывается в `vanity-results.txt`. Файл создаётся с правами 0600, путь задаёт `-o`. В терминал ключ выводится только с флагом `-k`. Остановка — Ctrl-C.

Импорт ключа в кошелёк:
- **EVM**: значение `private_key` (0x…) → MetaMask / Rabby, пункт «Import account → Private key».
- **TRON**: `private_key` (64 hex-символа) → TronLink, пункт «Import wallet → Private key».
- **TON**: `private_key` (64 hex) → MyTonWallet, пункт «Import wallet» → вставить ключ в поле для слов. Кошелёк должен быть версии **W5**.
- **Bitcoin**: `private_key_wif` (сжатый WIF, начинается с K или L). В Electrum: «Создать кошелёк → Импорт адресов или приватных ключей», вставить строку `electrum_import` — в ней уже стоит нужный тип (`p2wpkh:`, `p2pkh:` или `p2wpkh-p2sh:`), иначе Electrum покажет другой адрес. Sparrow и другие кошельки, принимающие WIF, тоже подходят — выберите тот же тип адреса.
- **Solana**: `private_key_base58` → Phantom / Solflare, пункт «Import private key». Для CLI сохраните `keypair_json` в файл и используйте его с `solana-keygen`.

## Безопасность ключей

В 2022 году из-за бага в profanity у Wintermute украли около $160M. Profanity запускал весь поиск от 32-битного seed, поэтому любой найденный адрес можно было пересчитать обратно в приватный ключ за часы. Здесь сделано так:

1. **Источник случайности только один** — `getrandom()` ОС, 256 бит (`src/rng.cpp`). Никаких mt19937, rand или seed от времени. Если getrandom вернул ошибку, программа завершается.
2. **EVM/TRON/Bitcoin — split-key.** CPU выбирает случайный ключ k0 и передаёт видеокарте только публичную точку k0·G. GPU ищет смещение. Итоговый ключ `±λ^e·(k0 + d) mod n` собирается на CPU. Полный ключ не попадает в видеопамять.
3. **Режим `--pubkey`** — когда этой машине не стоит доверять:
   ```bash
   # на офлайн-машине: свой ключ k0 и его публичный ключ (hex, сжатый или нет)
   vanity-gpu evm dead --pubkey 02ab...      # на машине с GPU — выдаёт только a и b
   vanity-gpu combine evm <k0> <a> <b>       # снова офлайн: итоговый ключ
   ```
   Формула простая: `key = (a·k0 + b) mod n`. По a и b без k0 ключ не восстановить.
4. **Solana и TON**: ключ кошелька — это seed, а скаляр = SHA-512(seed), поэтому split-key здесь невозможен. Seed'ы выдаёт ChaCha20 с 256-битным ключом из getrandom, у каждого блока свой счётчик.
5. **Каждая находка перепроверяется на CPU.** Отдельный, намеренно простой код (`src/hostcrypto.cpp`) заново выводит адрес из ключа. Если адрес не совпал с шаблоном, результат не выдаётся и печатается предупреждение. Сам CPU-код сверяется с библиотекой `cryptography` скриптом `tests/crosscheck.py`.

Красивый адрес не менее и не более надёжен, чем обычный. Учтите только адресный «poisoning»: злоумышленники генерируют адреса с такими же первыми и последними символами. Перед отправкой проверяйте адрес целиком.

## Как это устроено

- `multi`: одно ядро на все выбранные сети secp256k1 (или Solana+TON). Для каждой сети свой набор шаблонов в своём слоте константной памяти. Находка помнит свою сеть и перепроверяется на CPU по правилам этой сети. В режиме `--beauty` для TRON и `3…` сначала по старшим 64 битам числа проверяется, может ли ведущая серия вообще дотянуть до порога, и только потом считаются все 34 цифры base58 (это отдельный вариант ядра: без `--beauty` код этой проверки замедлял поиск `3…` на 16%). Ошибка этой проверки меньше 2, а допуск взят ±2, так что находки не теряются.
- `src/engine_secp.cu` — EVM/TRON/Bitcoin. Каждый поток идёт по своему окну точек P0 + d·G группами по 512. На группу приходится одна пакетная инверсия (трюк Монтгомери). Каждая точка даёт 6 ключей: ±y и эндоморфизм β, β². Адрес считается через keccak256. Для TRON префикс проверяется сравнением 160-битного числа с заранее посчитанным диапазоном, без base58 и sha256. Полный base58 (sha256d + деление) нужен только для суффиксов, `?` и `--beauty`. Для Bitcoin вместо keccak считается hash160 сжатого ключа (знак y меняет только префикс 02/03). `bc1q` сравнивается 5-битными масками прямо по hash160, контрольная сумма bech32 нужна только для последних 6 символов. `1…` и `3…` идут по диапазонам base58 как TRON.
- `src/engine_ed.cu` — Solana и TON: ChaCha20 → SHA-512 → умножение на базовую точку: 12 сложений с таблицей по 22-битным окнам цифр со знаком, без ветвлений (первое — просто загрузка точки, одно умножение вместо семи; в последнем не считается T) → пакетная инверсия Z на 64 ключа → сравнение диапазона или base58. Для TON дальше считается адрес кошелька W5: хэш ячейки данных и StateInit (3 вызова SHA-256), затем сравнение по 6-битным маскам base64. crc16 (последние 3 символа) считается, только когда шаблон или `--beauty` их затрагивают.
- `src/pattern.cpp` — разбор шаблонов, `-i`/`-l`/`[..]`, диапазоны base58, индекс для списков, оценка сложности.
- `src/cpu_secp.cpp` — поиск EVM/TRON/Bitcoin на процессоре (`--cpu`): поле secp256k1 на 64-битных словах, keccak на 8 ключей, SHA-256/RIPEMD-160 на 16.
- `cuda/` — арифметика полей на PTX, хэши.

## TON

Адрес — это кошелёк **W5 (wallet v5r1)**, mainnet, workchain 0, subwallet 0. Шаблон сравнивается с непересылаемой (non-bounceable) формой `UQ…`: её сейчас показывают кошельки. Bounceable-форма `EQ…` тоже выводится; у неё отличаются 1-й символ и последние 3.

- Первые два символа всегда `UQ`, третий — только `A`, `B`, `C` или `D`. Шаблон без `UQ` в начале ищется с 4-го символа: `cool` → `UQ?cool…`.
- Алфавит base64url: `A-Z a-z 0-9 - _`, регистр важен.
- Код адреса сверен с настоящим W5-кошельком в mainnet. Его публичный ключ взят из данных контракта, а пересчитанный адрес совпал с адресом в блокчейне. Этот кошелёк проверяется в `selftest` и `tests/crosscheck.py`.
- Стандартные TON-кошельки восстанавливаются из 24 слов (PBKDF2 на 100 000 итераций на кандидата), так что адреса из 24 слов здесь не ищутся. Ключ импортируется как приватный ключ. По документации MyTonWallet это поддерживает для W5. **Перед тем как отправлять средства, импортируйте ключ и убедитесь, что кошелёк показывает тот же адрес.**
